# Account deletion and Android Data safety

Source change for Android issue #25, coordinated with backend issue #8. This code is not in the already uploaded version 17; a new owner-built signed bundle is required after integration.

## Completion contract

`DELETE /users/me/account` sends the verified Firebase bearer and no caller-selected account ID/body. Only HTTP 200 with JSON `status: completed` permits device cleanup. HTTP 202, missing/unknown status, 409 support review and 503 pending preserve credentials and cached data for retry. The request carries an in-memory identity tag, checked by the bearer interceptor before dispatch. Its original signed token remains only in the ViewModel for retry after partial Firebase identity deletion; retries do not force token refresh. A different signed-in UID is refused. The token is never stored on disk or logged. Process death/expired-token partial cleanup still requires a verified support/operator path. Cleanup checks both current and cached identity before modifying device state. The confirmation dialog warns that account use pauses once destructive cleanup begins. Legacy chat ambiguity requires support review; no display-name deletion is permitted.

After completion a durable local-cleanup flag with its Firebase UID identity is written before clearing the Room profile, cards and events. Firebase sign-out precedes clearing, and cached profile writes require the currently signed-in matching UID under a mutex. FCM auto-init is disabled and its token deleted to remove notification subscriptions. Failed device cleanup remains pending and retries on restart before normal navigation or token registration. Completion starts a fresh activity task, disposing old fragment/viewmodel state and chat listeners. Topic registration and FCM auto-init resume only when a legitimate signed-in profile loads. App backups/transfers exclude local data to prevent restoring a deleted account cache. This does not remove historical OS/vendor backups already made.

## Chat rules rollout

New messages add `senderUid` from Firebase Authentication, checked against the Room profile external ID. Missing UID defaults to null so existing messages remain readable. `firebase/database.rules.json` defaults to denying all access; authenticated users without a private server `accountDeletionBlocks/$uid` marker can read event chats, and clients can only create fully validated messages attributed to their own UID. Client edits/deletes and unknown fields are denied. A server block prevents old cached tokens from reading/writing chats during deletion and after identity removal; clients cannot read or alter the block registry. Admin cleanup uses server credentials and bypasses client rules. This design does not implement event membership authorization.

The file is a proposed replacement, not deployed rules. Run the isolated harness in `firebase/tests` with `npm install` then `npm test` (JDK21 and Node22+). It uses only `demo-spontaniius` on localhost19000, no production credentials. Validate with Firebase emulator: unauthenticated reads/writes denied; authenticated own create/read allowed; spoofed UID, edits/deletes of own or others' messages, missing UID, malformed content and unknown fields denied; Admin cleanup still works. Deploy/verify rules before enabling backend sender attribution. Older version 17 writes no UID and becomes unable to send chat with these rules; coordinate the new app rollout. Never enable the attribution gate based only on client source or this JSON file.
